## 一句话结论

视频认为，AI 做设计的关键变化不只是模型变强，而是 Codex 能在更完整的上下文中工作：理解项目结构、设计规范、组件库、参考图和设计师的工作流程，并持续修改可运行的 UI。设计师的工作重心因此从“手动制作每个界面细节”转向“定义方向、提供约束、验证结果和做设计判断”。

## 视频原意概括

### 1. 从生成一张图到参与一个项目

过去 AI 生成的 UI 容易出现千篇一律的“AI 味”。视频将问题归因于上下文不足，而不只是模型能力不足。Codex 的项目、文件和对话上下文，使它可以围绕一个真实项目连续工作，而不是每次从零猜测需求。

### 2. 设计上下文决定输出质量

演示中先建立项目，再提供 `agents.md`（或同类项目说明文件）、参考图和设计规则。上下文可包括：

- 目标用户、使用场景和页面清单；
- 色彩、字体、间距、圆角、组件状态等设计系统规则；
- 参考图片、现有页面、文件结构和技术限制；
- 响应式断点、交互状态、可访问性和验收标准。

视频强调：上下文不必一开始就写得极端细；尤其是没有现成设计系统的新项目，先给清晰方向，再在迭代中补充约束。

### 3. Skills 和 MCP 是能力的放大器

视频展示了 Codex 的技能列表，例如 Audit、Image to Code、Design QA、Get Context、Ideate 等。技能把可重复的方法、检查清单和工具调用封装起来；MCP 则负责连接外部工具或数据源。两者与 `agents.md`、项目文件结合后，可以减少反复解释和手动切换。

视频中的判断是：写规则和配置会消耗更多 Token，但如果因此减少后续来回提示，整体成本可能值得。需要注意，这只是演示者的经验，不代表所有项目都能获得同样收益。

### 4. 先写清楚，再生成和迭代

演示用一个深色投资仪表盘作为例子，要求包含 Dashboard、Transactions、Budgets & Goals、Analytics & Reports、Settings 等页面。流程大致是：

1. 在项目中写清页面范围、视觉方向和参考图。
2. 让 Codex 读取项目说明和参考资料，生成第一版可运行 UI。
3. 通过浏览器或预览直接查看结果，而不是只看代码。
4. 用具体反馈逐项修改，例如图表坐标轴、悬停提示、选中点、颜色与当前指标一致等。
5. 继续刷新、检查和比较，直到结果达到验收标准。

### 5. “可运行结果”比静态设计文件更接近交付

视频后段展示从想法到部署（idea to deployment）的过程，并提出：与其发送需要额外解释的 Figma 文件，不如交付一个有真实功能的 URL 或可运行原型。这样评审者可以直接体验交互、响应式行为和状态变化。

这不意味着 Figma 失去价值。Figma 仍适合探索、协作和设计评审；视频强调的是，在需要验证产品行为时，可运行原型能减少“看图猜意图”的沟通成本。

## 设计师可复用的工作流

```text
需求/目标
  -> 项目说明与设计上下文
  -> 参考图、设计规则、Skills/MCP
  -> Codex 生成可运行原型
  -> 浏览器预览与 Design QA
  -> 具体反馈、逐项迭代
  -> 交付 URL/代码/资源，并由设计师验收
```

### 建议的项目说明文件结构

```md
# Project Brief
## Goal
- 要解决的问题、目标用户、成功标准

## Screens
- 页面清单、主要任务、关键状态

## Visual Direction
- 色彩、字体、层级、材质、参考图

## Interaction
- hover、loading、empty、error、success、responsive

## Constraints
- 技术栈、已有组件、资源格式、无障碍要求

## Acceptance Checklist
- 必须可操作的流程和需要人工检查的视觉细节
```

### 给 Codex 的任务表达方式

- 先说明目标和验收标准，再要求实现；不要只说“做得好看一点”。
- 用页面、状态、组件和行为描述需求，必要时附参考图或现有 URL。
- 把“必须遵守”和“可以探索”分开，避免约束互相冲突。
- 反馈要具体可验证：例如“图表 Y 轴显示指标和单位，悬停显示最近数据点”，而不是“优化图表”。
- 明确是否需要桌面端、移动端或特定断点；视频特别提醒，移动端适配不会自动发生。
- 每轮只处理一组相关问题，修改后重新预览并记录结果。

## 对视觉传达设计师的影响

### 机会

- **从静态画面扩展到体验**：设计师可以更快把版式、动效和交互状态做成可体验原型。
- **减少重复工程劳动**：切图、资源整理、组件拼装、页面回填和基础 QA 有机会自动化。
- **更早验证设计**：在低成本阶段验证响应式、交互路径和内容密度，减少后期返工。
- **设计系统能力更重要**：能把风格判断写成颜色、字体、间距、组件状态和验收规则的人，更容易获得稳定结果。
- **设计与开发协作更紧密**：设计师需要理解 HTML/CSS、组件和部署基本概念，才能判断生成结果是否真正可用。

### 不会自动消失的能力

- 研究用户、定义问题和判断优先级；
- 选择合适的视觉语言，处理文化语境与品牌差异；
- 发现模糊需求、冲突约束和不合理交互；
- 对版权、隐私、可访问性和最终质量负责。

## 风险与边界

- 视频是个人演示，不能把其中的效果当作 Codex 在所有项目中的保证。
- 设计规则、参考图和项目文件要保持一致；例如 Markdown 规定浅色、参考图却是深色，可能让模型产生歧义。
- 生成的代码和 UI 必须人工检查：布局、交互、键盘操作、对比度、移动端、性能和安全不能只看截图。
- 不要把含有客户资料、未公开产品信息或个人敏感数据的文件直接提供给外部工具；先做脱敏并确认权限。
- 参考图、字体、图标、图片和训练/生成素材要核对授权，不能因为“AI 生成”就忽略版权。
- 可运行原型不等于生产系统；上线前仍需要开发、测试、无障碍和安全审查。

## 我的分析

这条视频最值得保留的不是某个按钮或某个模型版本，而是“设计上下文工程”这一思路：设计师把目标、规则、参考和验收方法组织好，AI 才能持续参与项目。对视觉传达学习而言，可以把它当作一种从灵感到作品表达的练习：先建立视觉决策，再让 Codex 快速实现多个方向，最后用人的审美、叙事和用户判断筛选结果。

视频使用投资仪表盘和游戏 UI 做演示，和品牌海报、包装等视觉传达任务并不完全相同。因此，关于“Codex 已经懂设计师”的结论应理解为一种工作方式假设，仍需在自己的网页、作品集或交互项目中验证。

## 可执行的练习

1. 选择一个小型作品集首页，写一页 Project Brief，包含目标、页面、视觉规则和验收清单。
2. 准备一张参考图，同时写出 5 条可执行的视觉规则，不只写“高级”“简洁”。
3. 让 Codex 生成桌面端和移动端原型，比较哪些约束被正确执行，哪些需要补充说明。
4. 用 Design QA 清单检查对比度、间距、键盘操作、响应式、空状态和错误状态。
5. 保存每轮提示、截图和修改原因，形成自己的可复用 Skill 或项目模板。
